# API-Football 数据流程恢复

原来的深蓝金色页面保留。`刷新数据` 和 `重新预测` 调用同一条数据工作流：

API-Football `/fixtures?league=1&season=2026` → 保存真实赛程/比分 → 校验球队与完整小组赛 → 根据赛事 coverage 获取纪律详情 → 新建不可变预测快照 → 锁定已完赛结果 → 模拟未完赛比赛 → 原版页面展示。

## 数据与降级行为

- `GET /api/v2/data/status`：抓取时间、接口配置状态、失败原因、预测就绪状态和真实比赛列表。不会返回密钥。
- `POST /api/v2/data/refresh`：需要管理员 X-API-Key；请求体为 snapshot_id、simulation_count、seed，返回后台 job_id。`force=true` 可跳过五分钟缓存。
- 比分保留常规时间、加时和点球独立字段。比赛进行中显示实际比分，但不会误标为完场；现有模型是赛前模型，不做滚球预测。
- 真实比分先落库。缺失纪律事件、套餐不覆盖、球队映射不一致等情况会阻止新预测，而不会隐藏已经获取的真实比分或编造零红黄牌。
- 每次外部请求都计入共享每日配额。完成比赛详情最多 20 场一批，缓存六小时，覆盖信息缓存六小时。全部历史赛果进入预测时的近期表现状态，模型参数不在线重训。
- 原始训练数据来源仍为固定版本的历史国际比赛；赛事 API 补充当前赛事状态，两者不可互相替代。阵容等详情不会偷偷变成未经训练的新特征。
- 最新比赛与旧预测若不同步，页面显示两者各自时间。实际冠军展示为已知结果，不能将 100% 描述为预测准确率。

## 运行配置

后端保留原有 `API_FOOTBALL` / `API_FOOTBALL_KEY` / `APISPORTS_KEY` 任一非空配置；不会迁移或公开密钥。
`AUTO_REFRESH_DATA=true` 在服务启动后获取数据，再按 `DATA_REFRESH_INTERVAL_SECONDS`（默认 3600）刷新。Render 免费服务休眠时定时线程不会运行，恢复后会重新同步。
手动操作仍需 ADMIN_API_KEY，LLM 协调器的完整预测工具默认先同步 API；明确要求历史回放时可指定 refresh_data=false。

数据库新增 `v2_provider_feed`，不删除旧表；数据库故障不得被解释为接口成功。现有 SQLite 部署的缓存不跨容器重建持久化，长期运行应使用 PostgreSQL。

## 接口诊断与原有备用通道

API-Football 的套餐赛季限制、配额限制、认证失败分别显示可识别原因，不公开密钥或原始错误正文。原有 football-data.org 配置继续有效：主接口失败时读取该年世界杯比赛并明确标注备用来源；备用接口缺少纪律证据时仅展示事实，不冒充完整预测输入。两个接口失败均保留此前成功数据。页面读取接口最多等待 15 秒后显示错误，连接超时为 5 秒。

对于完整 104 场比赛均已结束的情形，备用通道保留原有固定淘汰赛图路径：检查轮次数量、逐轮参与者与上一轮胜者、时间顺序、签表连通性，并锁定全部实际胜者。无需推断缺失的纪律数据或重算小组排名，即可展示实际冠军及历史对阵结果；该结果标为 observed，不表示模型预测成功。API-Football 完整赛事适配器和小组排名引擎继续保留，赛中不满足输入要求的备用数据仍明确提示限制。
